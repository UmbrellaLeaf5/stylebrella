# Линтинг Kotlin

[English version](../../../en/code-style/kotlin/linting.md)

Целевая спецификация для `.kt` и `.kts` в дополнение к [общему линтингу](../linting.md) и [форматированию Kotlin](formatting.md). Команда `lint` сообщает только о нарушениях, не относящихся к форматированию. Опирайтесь на синтаксис Kotlin и разрешение символов; сообщайте только о нарушениях, которые анализатор может подтвердить. Движки линтинга и форматирования могут различаться.

## Имена, файлы и сериализация

Используйте `camelCase` для переменных, параметров, полей, функций и методов; `PascalCase` — для типов, включая классы данных, интерфейсы, объекты и перечисления; `SCREAMING_SNAKE_CASE` — для `const val`. Имя файла `.kt` пишется в `PascalCase` и совпадает с именем основного типа, а в файле только с функциями описывает назначение (`StringExtensions.kt`). Требуйте одно основное объявление класса, класса данных, интерфейса, объекта, перечисления или аннотации на файл. Сопутствующий `companion object` и `main` приложения не считаются отдельными типами. Самостоятельные типы размещаются в отдельных файлах; разрешённые вложенные категории констант не считаются самостоятельными основными типами.

Перед проверкой полей определяйте используемые сериализаторы. Каждое JSON-свойство должно явно объявляться через `@JsonProperty("snake_case")`. Тип с суффиксом `*Request` или `*Response` должен напрямую участвовать в сериализации HTTP-запроса или ответа в контроллере. Опирайтесь на разрешённые сигнатуры маршрутов или явные метаданные проекта, не угадывайте соглашения фреймворка. Для внутренних DTO выбирайте суффикс `*Input`, `*State` или `*Plan` по роли. Неразрешённое внешнее использование и соответствие имени роли оцениваются на ревью.

| Допустимо                                                                       | Нарушение                                                      |
| ------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| `val itemCount`, `fun calculateTotal`, `const val MAX_RETRIES`                  | `val item_count`, `fun CalculateTotal`, `const val maxRetries` |
| `FilterConfig.kt` с `data class FilterConfig`                                   | `filter_config.kt` или два самостоятельных типа в одном файле  |
| `@JsonProperty("created_at") val createdAt: Instant`                            | Нет аннотации или указано `@JsonProperty("createdAt")`         |
| `CreateOrderRequest` для HTTP; `CalculationInput` для внутреннего использования | `CalculationRequest`, используемый только внутри проекта       |

## Обработка null, преобразования, циклы и функции области видимости

- Запрещайте `!!` и вызовы напрямую разрешённых `requireNotNull` или `checkNotNull`. Для неверного ввода вызывающей стороны используйте `requireNotNullByName` или `requireFieldNotNullByName` (`IllegalArgumentException`), для ошибочного внутреннего состояния — `checkNotNullByName` или `checkFieldNotNullByName` (`IllegalStateException`), для обязательного поиска в репозитории — `findByIdOrThrow()`. Обычные `check` и `require` с логическим условием разрешены. Выбирайте подходящий вариант по контексту; автоматической замены нет.
- Разбирайте строки через `toDouble`, `toInt`, `toLong` или их nullable-варианты с явной обработкой null. Не используйте числовые преобразования для приведения типов объектов. Предпочитайте `as?` с обработкой null либо умное приведение через `is`. Используйте `as`, только когда тип гарантирован (например, доказанным инвариантом или в явно классифицированном тесте). Сообщайте о доказуемо небезопасном приведении, остальные неясные случаи оставляйте на ревью.
- Применяйте [общее правило циклов](../linting.md#выбор-вида-цикла). Однострочные `if` и `for` допустимы, если хорошо читаются.
- `run`, `let`, `apply`, `also` и `with` подходят для коротких преобразований, настройки объекта, логирования без разрыва цепочки и работы с nullable-значениями (`?.let`). Сообщайте о блоках длиннее пяти строк исполняемого кода в каноническом формате (выделите функцию), а также о разрешённых `run` или `with`, используемых только для группировки, если результат `Unit` не используется и блок не работает с объектом-получателем. Группировку несвязанных инструкций и лишнюю вложенность оценивайте на ревью. Не помечайте `apply`, который настраивает объект-получатель, только потому, что его блок возвращает `Unit`.

```kotlin
val itemId = request.itemId.requireFieldNotNullByName { "itemId" }
val processor = this.processor.checkFieldNotNullByName { "processor" }
val point = input as? Point ?: return

if (input is Point)
  processPoint(input)
```

Сообщайте о нарушении на `request.itemId!!` или `requireNotNull(request.itemId)`. Встроенные имена, переданные распознанным функциям именованной проверки на null, — метаданные проверяемого поля. На фактические предметные значения и значения по умолчанию, переданные вместе с ними, распространяется правило литералов.

## MARK, порядок методов и документация

Применяйте [общие правила MARK и приватных методов](../linting.md#текст-mark-и-важность-функций). Распознавайте `// MARK:` и используйте объявленную видимость Kotlin: учитывайте неявный `public`, но не приравнивайте `internal` к `private`. MARK контроллера может выглядеть как `// MARK: POST /api/order/calculate`.

Требуйте многострочный KDoc для функций, тело которых в каноническом формате занимает больше 15 непустых строк исполняемого кода без комментариев, для важных функций (включая первый приватный метод под структурным MARK) и для функций с собственным описательным MARK. Проверяйте привязку к объявлению: KDoc ставится перед аннотациями, если они есть.

Ставьте `/**` и `*/` на отдельные строки; используйте `*` перед текстом и ` *` на пустых строках. Начинайте с краткого описания без тега, затем добавляйте необязательные абзацы с подробностями, пустую строку KDoc и необходимые теги: `@param name description` в порядке сигнатуры, `@return description` для результата, отличного от `Unit`, и `@throws Type description` для известных исключений. Не ставьте двоеточие после имени и не повторяйте типы. Опускайте неприменимые теги, а если тегов нет, опускайте и пустую строку перед ними. Текст должен быть русским; при проверке языка не учитывайте идентификаторы, теги, ссылки и код. Сообщайте о явных нарушениях, неоднозначный текст оставляйте на ревью. Однострочный `/** ... */` не удовлетворяет требованию.

Проверяйте комментарии на той же строке для свойств класса данных, кроме `id`, `userId` и `itemId`. Группируйте параметры конструктора под заголовками `// repositories:`, `// mappers:` и `// services:` по суффиксам разрешённых типов. Учитывайте настроенные категории; неизвестные оставляйте на ревью.

```kotlin
// MARK: Calculate total
// --------------------------------------------------

/**
 * Вычисляет итоговую стоимость заказа.
 *
 * @param order заказ для расчёта
 * @return итоговая стоимость
 */
fun calculateTotal(order: Order) = calculator.total(order)
```

## Константы

Общие значения объявляйте под `object Constants` в `Constants.kt`, во вложенных объектах вроде `Math`, `Entity`, `ErrorDescription`, `Validation` и `Pattern`. Используйте `Constants.<Object>.<FIELD>` (например, `Constants.Validation.INVALID_EMAIL`), а не встраивайте регулярное выражение или предметное значение. [Общее правило встроенных литералов](../linting.md#константы-и-встроенные-литералы) разрешает текст сообщений в распознанных вызовах вывода, логирования и исключений. `@JsonProperty("user_id")` объявляет имя в схеме и освобождено от правила. Прочие литералы в тестах подчиняются правилам.

# Линтинг C++

[English version](../../../en/code-style/cpp/linting.md)

Целевая спецификация для `.cpp`, `.cc`, `.cxx`, `.h`, `.hpp` и `.hh` в дополнение к [общему линтингу](../linting.md) и [форматированию C++](formatting.md). Для применимых семантических правил используйте clang-tidy. Если `compile_commands.json` отсутствует, сообщайте о пропущенных семантических проверках; независимые файловые и синтаксические правила продолжают работать. Не проверяйте CMake как C++.

## Имена и структура файлов

Используйте `PascalCase` для классов, структур и перечислений и `snake_case` для функций, методов, переменных, полей и параметров. У приватных полей и методов одно начальное подчёркивание (`_gain_max_dbi`); не создавайте зарезервированные идентификаторы. Константы `const` и `constexpr`, включая локальные, именуйте в `SCREAMING_SNAKE_CASE`. Это не относится к cv-квалификаторам методов, объектов по указателю или ссылке либо параметров только для чтения. Имена пространств имён пишите строчными буквами. Для распознанных ключей JSON используйте `snake_case` (например, `"center_freq_hz"`). У приватной константы-члена сохраняйте начальное подчёркивание и пишите остальную часть имени прописными.

Проверяйте каталог пространства имён, наличие одного основного типа на файл, совпадение имени файла без расширения с именем единственного типа в `PascalCase` и `snake_case` для файлов вспомогательных функций. Используйте `.hpp` для заголовков проекта, кроме явно исключённых устаревших и сторонних файлов. В заголовке требуется `#pragma once` вместо макроса защиты от повторного включения. Для типов, общих для нескольких классов, используйте `shared/`, для типов, используемых одним классом, — `components/`, когда это подтверждено ссылками. Неполный граф зависимостей проверяйте на ревью. Размещайте объявления и реализации в деревьях `include/` и `src/` соответственно.

| Допустимо                                                      | Нарушение                                                         |
| -------------------------------------------------------------- | ----------------------------------------------------------------- |
| `include/app/core/Antenna.hpp` с объявлением `core::Antenna`   | `include/app/math/antenna.h` для того же типа проекта             |
| `void make_signal();`, `int _gain_max_dbi;` как приватный член | `void MakeSignal();`, `int gain_max_dbi;` как приватный член      |
| `constexpr int MAX_RETRIES = 3;` в пространстве имён констант  | `constexpr int maxRetries = 3;`                                   |
| `#pragma once` в заголовке проекта                             | Нет директивы или используется защита через `#ifndef` и `#define` |

## Использование языка и владение

- Запрещайте приведения в стиле C. По ситуации используйте `static_cast`, `dynamic_cast`, `const_cast` или `reinterpret_cast`. Например, `static_cast<double>(count)` допустимо, а `(double)count` вызывает диагностику. В распознанном контексте указателя используйте `nullptr`, а не `NULL` или `0`.
- Используйте `auto` для итераторов, сложных типов результата и подходящих захватов и результатов лямбд. Предпочитайте явные фундаментальные типы, если тип неочевиден. Сообщайте о распознаваемых формах вроде `auto count = 5;`, не пытаясь оценивать очевидность произвольного типа.
- Используйте `const` для неизменяемых локальных переменных (учитывайте разрешённые изменения и выход за пределы области), `constexpr` для констант времени компиляции, а методы отмечайте `const`, когда известно, что они не меняют объект и это совместимо с сигнатурой. Для фактических переопределений требуйте `override`. Отмечайте `final` классы, от которых не предполагается наследоваться; отсутствие подклассов само по себе не устанавливает намерение.
- Предпочитайте `std::unique_ptr` для исключительного владения, `std::shared_ptr` — только для действительно совместного владения, а `std::weak_ptr` — чтобы разрывать циклы совместного владения. Если владение или циклы не установлены, оставляйте случай на ревью. Не меняйте типы указателей автоматически.
- Предпочитайте `for` по [общему правилу циклов](../linting.md#выбор-вида-цикла). Запрещайте отдельные блоки в фигурных скобках, используемые только для группировки инструкций. Не путайте их с телом управляющей конструкции, функции, пространства имён, класса или с инициализатором. Блоки, необходимые для области видимости или времени жизни, оставляйте на ревью.

```cpp
class Loader final : public Input {
 public:
  Result read() const override;
};

auto position = items.begin();  // iterator
auto loader = std::make_unique<Loader>();  // exclusive ownership
```

## MARK, порядок методов и документация

Применяйте [общие правила MARK и приватных методов](../linting.md#текст-mark-и-важность-функций). Учитывайте доступ по умолчанию для `class` и `struct` и секции доступа; защищённые методы не считаются приватными. Для полей структур проверяйте наличие комментария на той же строке о смысле и единицах, кроме `id` и `name`. Используйте разделители и MARK как в `.cpp`, так и в заголовках.

Для каждого объявления функции, класса, структуры и перечисления в `.hpp` требуется многострочный Doxygen прямо над объявлением. Он также нужен первому важному приватному методу, покрытому `Private Helpers`, если у метода нет документированного объявления. Ставьте `/**` и `*/` на отдельные строки, используйте `*` перед текстом и ` *` на пустой строке. Начинайте с `@brief`: он объясняет, что делает функция или что представляет собой тип. Добавляйте `@details` для сложных алгоритмов или устройства типа, `@param name description` в порядке сигнатуры и `@return description` для результатов, отличных от `void`. Используйте `@throws Type description`, когда документируете известное исключение. Не ставьте двоеточие после имени параметра, не добавляйте `Type:` к описанию результата и опускайте неприменимые теги. Порог длинной функции (больше 15 непустых строк исполняемого кода без комментариев) или собственный MARK могут указывать, что подробности стоит проверить на ревью. Текст должен быть русским; при проверке языка не учитывайте теги, символы и код. Сообщайте об отсутствующих блоках, неверных обязательных тегах и однострочной документации (`///` или `/** @brief ... */`).

```cpp
// MARK: Read settings
// --------------------------------------------------

/**
 * @brief Загружает настройки из файла.
 * @param path путь к файлу настроек
 * @return прочитанные настройки
 */
Settings read_settings(const std::filesystem::path& path);
```

## Константы, исключения и консольный вывод

Размещайте общие значения в отдельном заголовке (например, `constants.hpp`) в пространстве имён констант проекта. Используйте категории вроде `math`, `entity`, `config`, `validation`, `pattern` и полностью квалифицированные ссылки, например `app::constants::config::CENTER_FREQ_HZ`. Не встраивайте общие числа, пути, шаблоны или значения по умолчанию. Применяйте [общее правило литералов](../linting.md#константы-и-встроенные-литералы).

Для стандартных исключений используйте форму `[Source] Message: key=value, key=value`, где `Source` — `Class::method` или `namespace::function`. Указывайте вызвавший сбой `path`, `field` или `type` перечисления, смотря что применимо. Используйте `std::invalid_argument` для неверного ввода и значений перечислений, `std::runtime_error` для сбоев ввода-вывода и окружения, `std::logic_error` для неверного состояния или порядка вызовов API. Проверяйте статически известные форму сообщения, источник и ключи. Тип исключения проверяйте, когда категория сбоя известна; остальные случаи оставляйте на ревью. Текст исключения, лога или печати может быть встроенным. Консольный вывод должен быть на английском и в ASCII: проверяйте литералы на ASCII, а смысл — на ревью.

```cpp
throw std::runtime_error("[Loader::load] Cannot read file: path=" + path.string());
```

Для распознанного файлового сбоя сообщайте о нарушении на `throw std::runtime_error("Cannot read file");`: не хватает источника и контекста. Не требуйте выносить сам текст сообщения в именованную константу.

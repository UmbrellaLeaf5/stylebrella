# Линтинг C++

[English version](../../../en/code-style/cpp/linting.md)

Область: `.cpp`, `.cc`, `.cxx`, `.h`, `.hpp`, `.hh`; CMake исключён. Для семантических правил используется база компиляции проекта. Без неё сообщайте о пропуске семантических проверок и продолжайте независимые файловые и синтаксические проверки. Видимость берётся из умолчаний `class`/`struct` и меток доступа; protected-методы не считаются приватными.

[Общие правила](../general/linting.md)

Каждый пример изолирует указанное правило. Примеры функций являются фрагментами; если правило не касается документации, пропущенная в примере обязательная документация считается присутствующей в полном исходном контексте.

## `naming`

<a id="stylebrella-linter-cpp-naming-1"></a>

<a id="sb-l-c-n-1"></a>

### SB-L-C-N-1 — Имена объявлений C++

`Stylebrella-linter-cpp-naming-1`

Требование PascalCase из [SB-L-G-N-1](../general/linting.md#sb-l-g-n-1) применяется к объявлениям `class`, `struct` и `enum`, включая `enum class`. Для функций, переменных, полей и параметров используется snake_case с учётом правила для констант [SB-L-C-N-2](#sb-l-c-n-2). Имена пространств имён пишутся строчными буквами. Префиксы приватных членов задаёт [SB-L-G-N-3](../general/linting.md#sb-l-g-n-3). О запрещённом начальном подчёркивании у публичных методов и самостоятельных функций сообщайте по [SB-L-G-N-4](../general/linting.md#sb-l-g-n-4).

Допустимые примеры показывают имена класса, структуры и `enum class`; каждый фрагмент взят из отдельного файла.

**C++**

**Допустимо:**

```cpp
class ConnectionPool {};
```

```cpp
struct RetryPolicy {
  int max_attempts;  // maximum number of attempts
};
```

```cpp
enum class ConnectionState { CONNECTING, CONNECTED, CLOSED };
```

В примерах ниже имена типов записаны в snake_case.

**Нарушение:**

```cpp
class connection_pool {};
```

```cpp
struct retry_policy {
  int max_attempts;  // maximum number of attempts
};
```

```cpp
enum class connection_state { CONNECTING, CONNECTED, CLOSED };
```

Пример показывает пространство имён, функцию, параметр и локальную переменную.

**C++**

**Допустимо:**

```cpp
namespace network {

int count_free_slots(int pool_size, int reserved_slots) {
  int available_slots = pool_size;
  available_slots -= reserved_slots;
  return available_slots;
}

}  // namespace network
```

Имя пространства имён начинается с заглавной буквы, остальные имена записаны в camelCase.

**Нарушение:**

```cpp
namespace Network {

int countFreeSlots(int poolSize, int reservedSlots) {
  int availableSlots = poolSize;
  availableSlots -= reservedSlots;
  return availableSlots;
}

}  // namespace Network
```

<a id="stylebrella-linter-cpp-naming-2"></a>

<a id="sb-l-c-n-2"></a>

### SB-L-C-N-2 — Имена значений const и constexpr

`Stylebrella-linter-cpp-naming-2`

Константа, объявленная `const` или `constexpr`, включая локальный объект и приватный член, называется в SCREAMING_SNAKE_CASE без префикса подчёркивания для приватных полей. Cv-квалификатор метода, const-объект по указателю или ссылке и параметр только для чтения не считаются объявлением константы.

**C++**

**Допустимо:**

```cpp
constexpr int MAX_RETRIES = 3;
```

**Нарушение:**

```cpp
constexpr int maxRetries = 3;
```

## `json`

<a id="stylebrella-linter-cpp-json-1"></a>

<a id="sb-l-c-j-1"></a>

### SB-L-C-J-1 — Ключи JSON в snake_case

`Stylebrella-linter-cpp-json-1`

Разрешённый ключ JSON в C++ пишется в snake_case. JSON-ключи считаются метаданными схемы и освобождены от правила встроенных литералов. Строки без установленной роли JSON не проверяются.

Доступ к JSON разрешён.

**C++**

**Допустимо:**

```cpp
record["center_freq_hz"];
```

Доступ к JSON разрешён.

**Нарушение:**

```cpp
record["centerFreqHz"];
```

## `files`

<a id="stylebrella-linter-cpp-files-1"></a>

<a id="sb-l-c-fi-1"></a>

### SB-L-C-FI-1 — Расширения заголовков и pragma once

`Stylebrella-linter-cpp-files-1`

Заголовок проекта имеет расширение `.hpp`, если явно не отмечен как устаревший или сторонний. В преамбуле обязателен `#pragma once`, макрос защиты всего файла запрещён.

Допустимый заголовок называется `Antenna.hpp`.

**C++**

**Допустимо:**

```cpp
#pragma once

class Antenna;
```

Нарушающий правило заголовок называется `Antenna.h`.

**Нарушение:**

```cpp
#ifndef ANTENNA_H
#define ANTENNA_H

class Antenna;

#endif
```

<a id="stylebrella-linter-cpp-files-2"></a>

<a id="sb-l-c-fi-2"></a>

### SB-L-C-FI-2 — Имена файлов, основные типы и структура исходников

`Stylebrella-linter-cpp-files-2`

Имя файла типа без расширения совпадает с именем его основного класса, структуры или перечисления и пишется в PascalCase. К классам применяется [SB-L-G-FI-1](../general/linting.md#sb-l-g-fi-1). В ограничение одного типа также входят именованные структуры и перечисления верхнего уровня; диагностика общего правила не дублируется. Вложенные типы и отдельные функции не учитываются. При нескольких типах имя файла проверяется по первому подходящему типу. Если есть только предварительные объявления, для проверки имени используется основное объявление. Файл вспомогательных функций имеет имя в snake_case. Каталог разрешённого пространства имён следует его пути относительно настроенного корня; объявления и реализации проекта находятся в `include/` и `src/` соответственно, а inline- и шаблонные определения допустимы в заголовках.

Допустимый путь: `include/app/core/Antenna.hpp`.

**C++**

**Допустимо:**

```cpp
namespace core {

class Antenna;

}  // namespace core
```

Путь с нарушением: `include/app/math/antenna.hpp`.

**Нарушение:**

```cpp
namespace core {

class Antenna;

}  // namespace core
```

<a id="stylebrella-linter-cpp-files-3"></a>

<a id="sb-l-c-fi-3"></a>

### SB-L-C-FI-3 — Общие типы и типы компонентов

`Stylebrella-linter-cpp-files-3`

При известном полном графе ссылок и хотя бы одном использующем классе тип размещается в `components/`, если класс один, и в `shared/`, если их два или больше. По неполному графу правило не применяется.

Допустимый путь: `shared/Point.hpp`; тип используется двумя классами.

**C++**

**Допустимо:**

```cpp
class Point {};
```

Путь с нарушением: `components/Point.hpp`; тип используется двумя классами.

**Нарушение:**

```cpp
class Point {};
```

## `types`

<a id="stylebrella-linter-cpp-types-1"></a>

<a id="sb-l-c-t-1"></a>

### SB-L-C-T-1 — Запрет приведений в стиле C

`Stylebrella-linter-cpp-types-1`

Приведения в стиле C запрещены. Диагностика на приведении, не на обычных группирующих скобках. Именованные приведения допустимы при корректных типах.

**C++**

**Допустимо:**

```cpp
static_cast<double>(count)
```

**Нарушение**:

```cpp
(double)count
```

<a id="stylebrella-linter-cpp-types-2"></a>

<a id="sb-l-c-t-2"></a>

### SB-L-C-T-2 — Nullptr для нулевых указателей

`Stylebrella-linter-cpp-types-2`

В подтверждённом контексте указателя вместо `NULL` или целого `0` требуется `nullptr`.

**Допустимо**:

```cpp
Widget* ptr = nullptr;
```

**Нарушение**:

```cpp
Widget* ptr = 0;
```

<a id="stylebrella-linter-cpp-types-3"></a>

<a id="sb-l-c-t-3"></a>

### SB-L-C-T-3 — Когда использовать auto

`Stylebrella-linter-cpp-types-3`

Для разрешённого типа итератора, замыкания лямбды или безымянного результата требуется `auto`; для непосредственного литерала фундаментального типа `auto` не допускается. Прочие случаи выбора вывода или явного типа проверяются отдельно.

**Допустимо**:

```cpp
int count = 5;
```

**Нарушение**:

```cpp
auto count = 5;
```

<a id="stylebrella-linter-cpp-types-4"></a>

<a id="sb-l-c-t-4"></a>

### SB-L-C-T-4 — Const и constexpr для локальных значений

`Stylebrella-linter-cpp-types-4`

Локальная инициализированная переменная должна быть `const`, если установлено отсутствие записи, изменяемого доступа или выхода из области и добавление сохраняет корректность и выбор перегрузок. Для константы требуется `constexpr`, если инициализация вычисляется при компиляции и такое объявление сохраняет контракт. Диагностируются только установленные случаи.

**Допустимо**:

```cpp
constexpr int MAX_RETRIES = 3;
```

**Нарушение**:

```cpp
const int MAX_RETRIES = 3;
```

<a id="stylebrella-linter-cpp-types-5"></a>

<a id="sb-l-c-t-5"></a>

### SB-L-C-T-5 — Const-методы и явный override

`Stylebrella-linter-cpp-types-5`

Метод экземпляра должен быть `const`, если полное определение доказуемо не меняет объект и квалификация сохраняет требования к сигнатуре и выбор перегрузки. Для фактического переопределения `override` обязателен в объявлении внутри класса. Отсутствие подклассов не вызывает диагностику `final`.

**Допустимо**:

```cpp
Result read() const override;
```

Это подтверждённое переопределение без спецификатора `override`.

**Нарушение:**

```cpp
Result read() const;
```

## `idioms`

<a id="stylebrella-linter-cpp-idioms-1"></a>

<a id="sb-l-c-id-1"></a>

### SB-L-C-ID-1 — Избыточные отдельные блоки

`Stylebrella-linter-cpp-idioms-1`

Диагностируется отдельный блок только для группировки, если он не создаёт необходимой границы видимости или времени жизни. Тела управляющих конструкций, функций, пространств имён, классов и инициализаторы исключаются. При неизвестном влиянии на видимость или время жизни диагностики нет.

**C++**

**Допустимо:**

```cpp
log();
flush();
```

**Нарушение:**

```cpp
{ log(); flush(); }
```

## `documentation`

<a id="stylebrella-linter-cpp-documentation-1"></a>

<a id="sb-l-c-d-1"></a>

### SB-L-C-D-1 — Когда объявлениям и функциям нужен Doxygen

`Stylebrella-linter-cpp-documentation-1`

Подробный Doxygen обязателен непосредственно над каждым объявлением функции в заголовочном файле (`.h`, `.hpp`, `.hh`); Doxygen также обязателен над объявлениями классов, структур и перечислений там же. Это относится и к приватным методам, конструкторам и деструкторам. Если определение в файле реализации разрешается в объявление из заголовка, диагностируйте прикреплённый к определению Doxygen как дублирование; наличие документации проверяйте у объявления в заголовке. Для функции, объявленной только в файле реализации, всё равно требуется краткое описание Doxygen у объявления или определения. Формат документации проверяйте по [SB-L-C-D-2](#stylebrella-linter-cpp-documentation-2). К лямбдам правило неприменимо.

**C++**

**Допустимо:**

```cpp
/**
 * @brief Сохраняет накопленные записи перед закрытием журнала.
 */
void flush_log() { log.flush(); }
```

**Нарушение:**

```cpp
void flush_log() { log.flush(); }
```

Блок Doxygen повторяется у определения в файле реализации.

**Нарушение:**

`log.hpp`:

```cpp
#pragma once

/**
 * @brief Сохраняет накопленные записи перед закрытием журнала.
 */
void flush_log();
```

`log.cpp`:

```cpp
#include "log.hpp"

/**
 * @brief Сохраняет накопленные записи перед закрытием журнала.
 */
void flush_log() { log.flush(); }
```

<a id="stylebrella-linter-cpp-documentation-2"></a>

<a id="sb-l-c-d-2"></a>

### SB-L-C-D-2 — Структура, теги и язык Doxygen

`Stylebrella-linter-cpp-documentation-2`

Перечисленные ниже теги параметров, результата и исключений обязательны для подробной документации в заголовках. Для функции, объявленной только в файле реализации, достаточно `@brief`; если есть необязательные теги, проверяйте их формат и описания.

Doxygen открывается `/**` и закрывается `*/` на отдельных строках; у каждой внутренней строки, в том числе пустой, есть звёздочка. Первый тег — непустой `@brief`. Для каждого именованного параметра требуется `@param name description` с непустым описанием в порядке сигнатуры, для установленного результата не `void` — `@return` с описанием, для известных выходящих исключений — `@throws Type description`. У конструкторов и деструкторов тега результата нет. Неприменимые теги, двоеточие после имени параметра и помета `Type:` результата опускаются. Проверка кириллицы и латиницы — как в [SB-L-K-D-2](../kotlin/linting.md#stylebrella-linter-kotlin-documentation-2). Даже при наличии блока диагностируются неверные разделители, пропущенные или неверные теги и пустые описания; `///` и однострочный блок не заменяют многострочный.

Пример — объявление в заголовке.

**C++**

**Допустимо:**

```cpp
/**
 * @brief Загружает настройки из последнего сохранённого профиля.
 * @return Настройки профиля с подставленными значениями по умолчанию.
 */
Settings read();
```

Примеры — объявления в заголовке.

**Нарушение:**

```cpp
/**
 * @brief Загружает настройки из последнего сохранённого профиля.
 */
Settings read();
```

```cpp
/**
 * Запускает задачи.
 */
void start_tasks();
```

## `constants`

<a id="stylebrella-linter-cpp-constants-1"></a>

<a id="sb-l-c-c-1"></a>

### SB-L-C-C-1 — Размещение и квалификация общих констант

`Stylebrella-linter-cpp-constants-1`

Именованная константа, используемая в двух или более исходных файлах, размещается в настроенном заголовке и пространстве имён констант проекта, в категории вроде `math`, `entity`, `config`, `validation`, `pattern`. Вне этого пространства для разрешённых общих констант требуется полностью квалифицированная ссылка.

**C++**

**Допустимо:**

```cpp
app::constants::config::CENTER_FREQ_HZ
```

Ссылка не квалифицирована и находится вне пространства имён.

**Нарушение:**

```cpp
CENTER_FREQ_HZ
```

<a id="stylebrella-linter-cpp-constants-2"></a>

<a id="sb-l-c-c-2"></a>

### SB-L-C-C-2 — Встроенные литералы и исключения для сообщений

`Stylebrella-linter-cpp-constants-2`

В местах использования общих чисел, шаблонов, путей и значений по умолчанию применяется [SB-L-G-C-1](../general/linting.md#stylebrella-linter-general-constants-1). Текст исключения, лога или вывода освобождается только в позиции сообщения по [SB-L-G-C-2](../general/linting.md#stylebrella-linter-general-constants-2).

**C++**

**Допустимо:**

```cpp
connect(app::constants::config::PORT);
```

**Нарушение:**

```cpp
connect(8080);
```

## `exceptions`

<a id="stylebrella-linter-cpp-exceptions-1"></a>

<a id="sb-l-c-ex-1"></a>

### SB-L-C-EX-1 — Структура сообщения исключения

`Stylebrella-linter-cpp-exceptions-1`

Статически известное сообщение стандартного исключения имеет форму `[Source] Message: key=value, key=value`. Source — охватывающий `Class::method` или `namespace::function`; подтверждённая ошибка пути, поля или перечисления требует ключ `path`, `field` или `type` соответственно. Известная структура и ключи проверяются и при вычисляемом значении. Текст не генерируется.

**C++**

**Допустимо:**

```cpp
throw std::runtime_error("[Loader::load] Cannot read file: path=" + path.string());
```

Пример подтверждённой ошибки работы с файлом.

**Нарушение:**

```cpp
throw std::runtime_error("Cannot read file");
```

<a id="stylebrella-linter-cpp-exceptions-2"></a>

<a id="sb-l-c-ex-2"></a>

### SB-L-C-EX-2 — Тип исключения по категории сбоя

`Stylebrella-linter-cpp-exceptions-2`

Для подтверждённой категории ошибки требуется `std::invalid_argument` при неверном входе или значении перечисления, `std::runtime_error` при ошибке ввода-вывода или окружения, `std::logic_error` при неверном внутреннем состоянии или порядке вызовов API. Неизвестная категория не вызывает диагностику типа.

Категория сбоя — неверные входные данные.

**C++**

**Допустимо:**

```cpp
throw std::invalid_argument(message);
```

Категория сбоя — неверные входные данные.

**Нарушение:**

```cpp
throw std::runtime_error(message);
```

<a id="stylebrella-linter-cpp-exceptions-3"></a>

<a id="sb-l-c-ex-3"></a>

### SB-L-C-EX-3 — Сообщения консоли в ASCII

`Stylebrella-linter-cpp-exceptions-3`

В статически известном тексте разрешённого сообщения консоли допускается только ASCII. Язык произвольных строк и содержимое динамических значений не определяются.

**Допустимо**:

```cpp
std::cout << "Loaded";
```

**Нарушение**:

```cpp
std::cout << "Загружено";
```

## Рекомендации (без диагностики)

Используйте `std::unique_ptr` для исключительного владения, `std::shared_ptr` только для совместного, `std::weak_ptr` — для разрыва циклов. Перед удалением отдельного блока проверьте область видимости и время жизни. Используйте `final`, когда наследование намеренно запрещено. Сложные алгоритмы и устройство типа поясняйте в `@details`. Сообщения для консоли пишите на английском. Если категория ошибки не установлена, проверяйте тип исключения на ревью.

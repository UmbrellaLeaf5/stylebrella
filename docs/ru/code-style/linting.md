# Общие правила линтинга

[English version](../../en/code-style/linting.md)

Целевая спецификация пресета `template`. Команда `lint` сообщает о нарушениях этой страницы и правил языка: [Python](python/linting.md), [Kotlin](kotlin/linting.md), [C++](cpp/linting.md). Команда `check` дополнительно проверяет [форматирование](formatting.md). Примеры иллюстрируют одно правило; тот же фрагмент может вызывать и другую диагностику. Требования **для ревью** обязательны, но линтер сообщает о нарушении только при наличии проверяемых признаков. Наличие правила в спецификации не означает, что оно уже реализовано.

## Имена объявлений

Проверяйте имена по виду объявления: локальные переменные, параметры, поля, функции, типы и константы подчиняются соглашениям своего языка. Не выводите назначение символа только из его написания. Имена должны быть содержательными и указывать единицы измерения, где это уместно; качество имён оценивается на ревью. Сообщайте о нарушении на объявлении, не переименовывая его и не меняя внешний API автоматически.

| Язык   | Допустимо                    | Нарушение                   |
| ------ | ---------------------------- | --------------------------- |
| Python | `total_count = count()`      | `totalCount = count()`      |
| Kotlin | `val totalCount = count()`   | `val total_count = count()` |
| C++    | `int total_count = count();` | `int totalCount = count();` |

## Ключи JSON

Проверяйте ключи, если поле сериализации или обращение к JSON можно определить статически. Применяйте регистр и правила объявления соответствующего языка. Не считайте произвольные строки ключами и не меняйте имена в протоколе обмена. Допустимый ключ схемы всё равно может требовать именованной константы в месте использования.

| Язык                            | Допустимо                  | Нарушение                 |
| ------------------------------- | -------------------------- | ------------------------- |
| Python (проект со `snake_case`) | `"user_id"`                | `"User-ID"`               |
| Kotlin                          | `@JsonProperty("user_id")` | `@JsonProperty("userId")` |
| C++                             | `"user_id"`                | `"userId"`                |

## Текст MARK и важность функций

Пишите понятный английский текст с прописной буквы или целиком ПРОПИСНЫМИ. Отклоняйте пустые заголовки, заголовки со строчной буквы и заголовки, состоящие только из идентификатора объявления в `camelCase` или `PascalCase`. Качество текста проверяется на ревью. Для HTTP-обработчика заголовком могут служить метод и путь. Функция нетривиальна, если исполняемый код занимает несколько строк, содержит несколько инструкций или вложенный управляющий поток. Считайте исполняемые строки после приведения к каноническому формату: ручные переносы не должны позволять обходить правило. Функция или метод считаются важными, если у них два или более разных места использования, разрешённых в проекте, даже внутри одного вызывающего метода. Не учитывайте саморекурсию, комментарии и неразрешённые ссылки. Для публичных нетривиальных и для важных функций требуется описательный MARK; допустимо покрытие корректной группой. Для тривиальной неважной функции достаточно разделителя.

| Язык   | Допустимо над объявлением | Нарушение над тем же объявлением |
| ------ | ------------------------- | -------------------------------- |
| Python | `# MARK: Build response`  | `# MARK: buildResponse`          |
| Kotlin | `// MARK: Build response` | `// MARK: buildResponse`         |
| C++    | `// MARK: Build response` | `// MARK: BuildResponse`         |

## Группы MARK и соседство

Группы необязательны. `MARK: <title> [group:N]` покрывает ровно `N` следующих объявлений функций или методов того же уровня в текущей области; `N` — десятичное целое не меньше 2. Вложенные определения и прочие объявления не считаются. Сообщайте о недопустимом счётчике или о том, что другой MARK либо конец области прерывает группу раньше срока. Следующее за `N` объявление уже за пределами группы. Запрещены два MARK на одном уровне без объявления или содержательной инструкции между ними; пустые строки и разделители не разрывают соседство. `Private Helpers` — структурный заголовок без счётчика, и последующие описательные MARK не закрывают эту секцию. Не ставьте описательный MARK сразу после структурного; одна группа со счётчиком не заменяет отдельный публичный MARK и секцию приватных методов.

Структурный заголовок покрывает первый приватный метод. Если он важный, вместо второго MARK у него должен быть блок документации для соответствующего языка. Такой блок не разрывает соседство MARK.

| Язык   | Допустимо                                                           | Нарушение                                            |
| ------ | ------------------------------------------------------------------- | ---------------------------------------------------- |
| Python | `# MARK: Load adapters [group:2]`, затем две функции одного уровня  | После заголовка до конца области только одна функция |
| Kotlin | `// MARK: Load adapters [group:2]`, затем два метода одного уровня  | Другой MARK перед вторым методом                     |
| C++    | `// MARK: Load adapters [group:2]`, затем две функции одного уровня | `// MARK: Load adapters [group:1]`                   |

| Язык   | Допустимо для первого важного приватного метода                           | Нарушение                                                            |
| ------ | ------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| Python | `# MARK: Private Helpers`, разделитель, `_read` с многострочным docstring | Нет docstring или под заголовком стоит ещё один `# MARK: Read input` |
| Kotlin | `// MARK: Private Helpers`, разделитель, KDoc, `private fun readInput`    | Нет KDoc или подряд с заголовком стоит `// MARK: Read input`         |
| C++    | `// MARK: Private Helpers`, разделитель, Doxygen, приватный `_read`       | Нет Doxygen или подряд с заголовком стоит `// MARK: Read input`      |

## Обязательные секции класса

В конкретном классе с публичными и приватными методами требуйте не менее двух MARK: один привязан к публичному методу (автор выбирает его сам, если ни один метод не признан важным автоматически), другой — `MARK: Private Helpers`. У класса без приватных методов форматтер ставит комментарий-заглушку; пустой MARK не требуется. Минимум не распространяется на интерфейсы и классы, используемые только как DTO.

| Язык   | Допустимый порядок членов                                                              | Нарушение                                              |
| ------ | -------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| Python | `# MARK: Read input`, `read`, `# MARK: Private Helpers`, `_read`                       | У публичного `read` в том же классе только разделитель |
| Kotlin | `// MARK: Read input`, `fun read`, `// MARK: Private Helpers`, `private fun readInput` | Заголовок секции — единственный MARK                   |
| C++    | `// MARK: Read input`, публичный `read`, `// MARK: Private Helpers`, приватный `_read` | Оба MARK описывают приватные методы                    |

## Порядок приватных методов

В классах, на которые распространяется правило, размещайте приватные методы после всех публичных. Видимость определяется синтаксисом или соглашением языка, а не использованием. Сообщайте о нарушении на объявлении, стоящем не на своём месте. Не переставляйте объявления автоматически.

| Язык   | Допустимо                                 | Нарушение                                 |
| ------ | ----------------------------------------- | ----------------------------------------- |
| Python | `read`, затем `_read`                     | `_read`, затем `read`                     |
| Kotlin | `fun read`, затем `private fun readInput` | `private fun readInput`, затем `fun read` |
| C++    | `public: read`, затем `private: _read`    | `private: _read`, затем `public: read`    |

## Комментарии у полей и язык комментариев

Требуйте комментарий на той же строке для полей, указанных в правилах языка, за исключением явно перечисленных самопоясняющих имён. Комментарий поясняет смысл и, где уместно, единицы измерения. Линтер проверяет наличие, а качество текста и правильность единиц оцениваются на ревью. Текст MARK пишется по-английски. Обычные комментарии могут быть английскими или русскими; для новых и изменённых предпочтителен русский. Для docstring, KDoc и Doxygen действуют правила языка.

| Язык   | Допустимо                                           | Нарушение                                 |
| ------ | --------------------------------------------------- | ----------------------------------------- |
| Python | `df_hz: float = 0.0  # offset from center, Hz`      | То же поле dataclass без комментария      |
| Kotlin | `val dfHz: Double = 0.0, // offset from center, Hz` | То же свойство data class без комментария |
| C++    | `double df_hz = 0.0; // offset from center, Hz`     | То же поле структуры без комментария      |

## Константы и встроенные литералы

Определяйте каждое общее предметное значение один раз в отведённом для языка контейнере констант. Требуйте именованное значение для встроенных данных, которые не подпадают под исключения: в том числе предметных значений по умолчанию, путей, регулярных выражений, коэффициентов пересчёта, значений точности, специальных значений и тестовых входов. Разрешайте `0`, `1` и `""` для тривиальной инициализации (в том числе эквивалентные типизированные ноль и единицу), а также логические и null-значения языка. Разрешайте встроенный **текст** сообщения в разрешённых позициях вывода, логирования и исключений, включая интерполируемый текст. Исключение не распространяется на предметные данные, передаваемые аргументами. Учитывайте только явно описанные исключения для синтаксиса, схем и метаданных, а не произвольные имена вызовов или строки. Показывайте нарушение на литерале; не выносите его автоматически и не считайте одинаковые значения тождественными по смыслу.

| Язык   | Допустимо                                                                     | Нарушение        |
| ------ | ----------------------------------------------------------------------------- | ---------------- |
| Python | `connect(Constants.Network.DEFAULT_PORT)`; `raise ValueError("Invalid port")` | `connect(8080)`  |
| Kotlin | `connect(Constants.Network.DEFAULT_PORT)`; `logger.warn("Invalid port")`      | `connect(8080)`  |
| C++    | `connect(app::constants::network::DEFAULT_PORT);`                             | `connect(8080);` |

## Выбор вида цикла

Для обхода известного диапазона или коллекции предпочтителен `for`, для циклов с состоянием или сложным условием завершения — `while`. Сообщайте только о распознанном цикле со счётчиком, эквивалентном обычному обходу; случаи с неясными обновлениями, побочными эффектами или остановкой оставляйте на ревью. Форматтер не меняет вид цикла.

| Язык   | Допустимо                                     | Кандидат на диагностику                                                                                    |
| ------ | --------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| Python | `for item in items: visit(item)`              | `i = 0; while i < len(items)` с единственным обычным шагом `i += 1`                                        |
| Kotlin | `for (item in items) visit(item)`             | `while (i < items.size)` с индексом, который начинается с нуля и увеличивается один раз на каждой итерации |
| C++    | `for (const auto& item : items) visit(item);` | `while (i < items.size())` с тем же шаблоном счётчика                                                      |

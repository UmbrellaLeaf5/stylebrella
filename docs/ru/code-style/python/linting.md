# Линтинг Python

[English version](../../../en/code-style/python/linting.md)

Целевая спецификация для `.py` в дополнение к [общему линтингу](../linting.md) и [форматированию Python](formatting.md). Ноутбуки отложены. Включайте правила Ruff `E`, `F`, `B`, `UP`, `RUF` и `PL`, исключая `RUF001`, `RUF002`, `RUF003`, `F405`, `F403`, `PLR0912`, `PLR0915`, `PLR0913`, `PLR0911`, `B008`, `PLW2901`, `RUF012`, `PLC2401` и `PLR2004`. Не допускайте оставшихся предупреждений и ошибок. Порядок импортов (`I`) относится к проверке форматирования, а не к `lint`. Не добавляйте `# noqa`, исключения для отдельных файлов или дополнительные исключения без явного разрешения. Pyright в режиме `basic` — запланированный движок: после интеграции его ошибки типов должны блокировать проверку Python.

## Имена и аннотации

Для функций, методов, переменных, параметров и полей требуйте `snake_case`; для классов, dataclass и исключений — `PascalCase`; для констант — `SCREAMING_SNAKE_CASE`; для обобщённых переменных типа — `T` или `PascalCase` с префиксом `T`. Внутренние символы, статус которых известен, начинаются с подчёркивания (`_cache`, `_build_response`, `_InternalType`). Не считайте символ внутренним только из-за отсутствия ссылок на него. Ключи JSON должны соответствовать выбранному в проекте соглашению (`snake_case` или `camelCase`) во всём проекте.

Требуйте аннотации параметров и результата функций и методов, включая `-> None`, где это уместно; параметры-получатели `self` и `cls` освобождены. В Python 3.10+ предпочитайте `T | None` вместо `Optional[T]`. Сообщайте о явном `Any`, который разрешается в `typing.Any`; по ситуации используйте `object`, конкретный тип, `Protocol` или ABC. Для параметров и результатов, распознанных как файловые пути, используйте `pathlib.Path`, а не `str`. Не помечайте посторонние строки только по имени.

| Допустимо                                               | Нарушение                                                                                                 |
| ------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| `def load_config(path: Path) -> Config: ...`            | `def loadConfig(path): ...` (имя и отсутствующие типы)                                                    |
| `def find_user(user_id: str) -> User \| None: ...`      | `def find_user(user_id: str) -> Optional[User]: ...`                                                      |
| `_cache`, `_InternalType`, `TItem`, `DEFAULT_TIMEOUT_S` | `Cache` для внутренней переменной, `ItemT` для обобщённой переменной типа, `defaultTimeout` для константы |

## Использование языка

- Используйте f-строки для интерполяции. Сообщайте об известном строковом форматировании через `%` или вызов `.format()`, но не об арифметическом остатке. Если при отладке важно точное представление значения, предпочитайте `repr()` или `!r` (ревью). Распознанные вызовы логирования — исключение: используйте отложенное форматирование через `%` с отдельными аргументами, например `logger.debug("Loaded %r", config)` вместо `logger.debug(f"Loaded {config!r}")`.
- Используйте `with` для управления временем жизни файловых дескрипторов, соединений, блокировок и пользовательских ресурсов. Предпочитайте `with path.open() as stream:` распознанному вызову `path.open()` без управления временем жизни. Реализуйте `__enter__` и `__exit__` или используйте `contextlib.contextmanager` для пользовательских ресурсов. Если владение или время жизни нельзя определить, оставьте случай на ревью.
- Используйте включения для простых преобразований, не более двух уровней вложенности: считайте вложенные узлы включений и вложенные секции генераторов. Для ленивого обхода больших наборов данных используйте генераторные выражения. Достаточно ли велик набор данных — вопрос ревью. Применяйте [общее правило циклов](../linting.md#выбор-вида-цикла).
- Предпочитайте `pathlib.Path` вместо `os.path`. Используйте `dataclasses.dataclass` для структур данных, Pydantic `BaseModel` для проверяемой конфигурации, `Enum` или `IntEnum` вместо наборов строковых констант, образующих перечисление, замороженные dataclass для неизменяемых данных и `typing.Protocol` для структурных интерфейсов. Сообщайте о распознанных вызовах `os.path` и других явных нарушениях; классификация произвольных структур и необходимость неизменяемости остаются на ревью.
- Исполняемые скрипты проектов с `.venv` или `uv` начинаются с `#!/usr/bin/env python3`. Скрипты, предназначенные и для импорта, и для запуска, защищают выполнение условием `if __name__ == "__main__":`. Определяйте статус скрипта или точки входа по метаданным проекта либо явным соглашениям, а не по произвольному содержимому файла.
- В распознанном рабочем коде используйте `logging`, а не `print()`. Выбирайте подходящий уровень DEBUG, INFO, WARNING, ERROR или CRITICAL (ревью). Статически распознаваемый текст консольных сообщений должен быть на английском и в ASCII: сообщайте о символах вне ASCII, а язык и динамическое содержимое проверяйте на ревью.

```python
def load_config(path: Path) -> Config:
  with path.open() as stream:
    config = parse_config(stream)

  logger.debug("Loaded %r", config)

  return config
```

## Импорты и экспорт

Запрещайте импорт со звёздочкой в рабочем коде, кроме реэкспорта из `__init__.py`, ограниченного явным `__all__`. Публичный API пакета объявляйте в `__all__`, а не через избыточный псевдоним или подавление диагностики. Сообщайте о циклическом импорте, только если цикл подтверждён по разрешённым импортам проекта; динамические импорты оставляйте на ревью. Устраняйте циклы изменением структуры, а ленивые импорты вводите только при необходимости.

```python
# __init__.py — explicit exports
from .service import UserService


__all__ = ["UserService"]
```

## MARK, порядок методов и документация

Применяйте [общие правила MARK и методов](../linting.md#текст-mark-и-важность-функций). Маркер — `# MARK:`. Одно начальное подчёркивание обозначает приватный метод; специальные методы с двойными подчёркиваниями (`__init__` и другие) не считаются приватными вспомогательными методами. Общие секция и порядок применяются к приватным методам класса, а при необходимости — и к сгруппированным приватным функциям. Неразрешённая динамическая ссылка не делает функцию важной.

Требуйте многострочный docstring в стиле Google в качестве первой инструкции каждой нетривиальной публичной функции, каждой длинной или важной функции и каждой функции с собственным описательным MARK. Первый важный приватный метод в секции `Private Helpers` тоже требует docstring, хотя у него нет собственного MARK. Тело считается длинным, если в каноническом формате оно содержит более 15 непустых строк исполняемого кода без комментариев и существующего docstring. Тривиальные самопоясняющие функции и обычные приватные методы могут обходиться без docstring, если ни одно требование не применяется.

Открывающие и закрывающие `"""` ставьте на отдельные строки. Начинайте с краткого описания, затем при необходимости добавляйте подробные абзацы и подходящие английские разделы `Args:`, `Returns:`, `Raises:` (а для документированных классов — `Attributes:`). Между абзацами и разделами оставляйте одну пустую строку. Содержимое раздела отступает на два пробела относительно заголовка. Для параметров и атрибутов используйте `name: Description`, не повторяя типы из сигнатуры; в `Returns:` пишите описание, для известных исключений, выходящих наружу, используйте `ExceptionType: Description` (символы можно брать в обратные кавычки). Соблюдайте имена и порядок объявления, исключая неявные параметры-получатели. Неприменимые разделы опускайте. Сообщайте о неверных или отсутствующих разделах, если их применимость установлена. Предпочтителен русский текст; его качество оценивается на ревью. Однострочный docstring не заменяет обязательный блок.

Для свойств dataclass требуйте комментарий на той же строке о смысле и единицах, кроме `id`, `user_id` и `item_id`. Группируйте параметры `__init__` под заголовками вроде `# repositories:`, `# mappers:` и `# services:`, если разрешённые типы имеют суффиксы `Repository`, `Mapper` и `Service` соответственно. Учитывайте настроенные расширения; неизвестные категории оставляйте на ревью.

```python
# MARK: Load configuration
# --------------------------------------------------


def load_config(path: Path) -> Config:
  """
  Загружает конфигурацию из файла.

  Args:
    path: Путь к файлу конфигурации.

  Returns:
    Прочитанная конфигурация.
  """

  config = parse_config(path)
  validate_config(config)

  return config
```

## Константы и тесты

Общие значения размещайте в `constants.py` внутри `Constants.Math`, `Constants.Entity`, `Constants.Validation`, `Constants.Pattern` или подходящей дополнительной категории для другой предметной области. Используйте `Constants.<Category>.<FIELD>` и прописные имена, например `Constants.Math.DEG_TO_RAD` вместо `pi / 180.0` в месте вызова. Применяйте [общие правила встроенных литералов](../linting.md#константы-и-встроенные-литералы). `"__main__"` в условии точки входа, разрешённые имена из `__all__` и декларативные имена параметров или фикстур pytest — синтаксические метаданные, а не тестовые данные.

Используйте pytest и имена `test_<module>.py`. Общие фикстуры с одной задачей помещайте в `conftest.py`, а повторяющиеся сценарии объединяйте через `@pytest.mark.parametrize`. Используйте `pytest.MonkeyPatch` для подмен на уровне модуля, `unittest.mock` — на уровне экземпляра. Тесты, зависящие от окружения, отмечайте `skip` или `skipif`. Проверяйте разрешённые вызовы фреймворка и имена; ответственность фикстуры и необходимость параметризации определяйте на ревью. Именуйте тестовые входы, не встраивайте магические значения в проверки или списки параметров.

```python
@pytest.mark.parametrize("name,valid", Constants.TestData.NAME_CASES)
def test_validate_name(name: str, valid: bool) -> None:
  assert User.is_valid_name(name) == valid
```
